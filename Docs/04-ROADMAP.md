# План аналитики и выпуска

**Статус:** дорожная карта для ревью, не детальный план написания кода. Аудитория подтверждена: открытый сервис для сообщества. Сроки и бюджет определяются после уточнения команды и результатов прототипов.

## 1. Что уже сделано

- Изучены публичные страницы SIGame и SI Browser, исходники SI/SIOnline и первичные технические документы.
- Разделены подтверждённые факты, рекомендации и непроверенные гипотезы.
- Сформулированы бизнес-требования, функциональный объём и измеримые цели.
- Предложены профиль `.siq`, архитектура, механизм синхронизации и маршрут разрешённого наполнения каталога.
- Создан локальный репозиторий с документами в `Docs`.

Не выполнены: интервью, UX-тестирование, запуск игровых прототипов, нагрузочные испытания, согласование прав и разработка приложения. Они являются следующими работами.

## 2. Аналитика до основной разработки

| Работа | Исполнитель / участники | Проверяемая гипотеза | Результат и критерий выхода |
|---|---|---|---|
| Интервью | Продуктовый ответственный; 5 ведущих, 5 авторов, 5 игроков | Единый сценарий решает повторяющуюся проблему | Список наблюдаемых проблем с частотой; три приоритетных сценария |
| Сравнение пользовательских путей | Аналитик/дизайнер | Улучшение можно показать на реальной задаче | Пройти поиск → запуск и создание → публикацию в существующих решениях; записать время, шаги и ошибки; не оценивать по впечатлению |
| Корпус SIQ | Backend + QA + авторы | Предложенный профиль покрывает ≥95% выборки | 100 разрешённых пакетов, частоты конструкций, таблица несовместимостей и уточнённый MVP |
| Права и каталог | Владелец продукта + профильный специалист | Доступен устойчивый канал наполнения | Условия источника, модель разрешений и удаления; при отсутствии экспорта — план привлечения авторов |
| UX-прототип | Дизайнер + 8–10 участников | Первый ведущий запускает игру без обучения | Проверить комнату, мобильную кнопку и редактор; минимум 8 из 10 проходят ключевую задачу |
| Технический прототип | Backend + frontend | Выбранный стек проходит бюджет | Сравнение Rust/Go, мобильная сборка, round-trip SIQ и сетевые сценарии |
| Экономика | Продукт + инфраструктура | Бесплатный базовый сервис имеет управляемую себестоимость | Модель при 100/1 000/10 000 подключениях; реальные размеры файлов, условия провайдеров и три сценария потребления |
| Эксплуатация и данные | Инфраструктура + продукт | Открытый сервис можно поддерживать | Регион, политика хранения, резервирование, владелец инцидентов и модерация |

Стоимость ИИ оценивать на **принятый автором вопрос**, включая отклонённые варианты и проверки. Перед выбором платной модели провести интервью о готовности платить; цены сейчас не выдумывать.

## 3. Этапы реализации

| Этап | Поставляемый результат | Зависимость | Критерий перехода |
|---|---|---|---|
| A. Согласование | Принятые D-01…D-09, уточнённые границы и владельцы работ | Ревью этого комплекта | Ясны аудитория, формат, правила, ограничения и бюджет |
| B. Проверка рисков | SIQ-конвертер на корпусе, тест комнаты, мобильный прототип | A, доступные тестовые материалы | Нет скрытой потери данных; стек выбран по измерениям; правила нажатия согласованы |
| C. Закрытая игровая альфа | Вход, комнаты, ведущий, табло, медиа, спецвопросы, финал и восстановление | B | Полный матч на 6 реальных устройствах; повторы/разрывы не портят счёт |
| D. Полный авторский цикл | Редактор, версии, каталог, публикация, модерация, ИИ и MCP | Модель пакета из B и API из C | Пакет создаётся/генерируется, проходит ревью и разыгрывается внутри сервиса |
| E. Пилот сообщества | Участие авторов, разрешённый каталог, аналитика, исправления | C + D | Продуктовые сценарии BR-01…08 проверены на пилоте; критические проблемы исправлены |
| F. Публичный запуск | Наблюдаемость, резервирование, защита, рабочая поддержка | E | Пройдены предрелизные проверки NFR, восстановление копии и 10 000 соединений; нагрузочный лимит сервиса не выше испытанного |
| G. Рост | Расширенные типы, совместная работа, турниры/голос при спросе | Метрики после F | Каждая функция обоснована использованием и затратами |

Месячная доступность NFR-08 и полевые метрики NFR-05 подтверждаются после запуска; до него проверяются мониторинг и лабораторные показатели.

При нехватке бюджета уменьшаем глубину и темп выпуска явно. Нельзя незаметно исключить редактор, каталог или ИИ/MCP и назвать результат выполнением исходной концепции.

После этапа A нужны отдельные небольшие спецификации: **формат и медиа**, **игровой движок и сеть**, **авторская работа и публикация**, **ИИ/MCP**, **эксплуатация**. Детальные задачи разработки опираются на их согласованные интерфейсы.

## 4. Проверки перед запуском

| Проверка | Что должно быть доказано |
|---|---|
| Совместимость | Пакеты P0 открываются, редактируются, играются и экспортируются; неподдержанное не маскируется |
| Детерминированность | Одна команда не меняет счёт дважды; один вопрос не даёт двух победителей кнопки |
| Сбой сети | Перезагрузка, смена сети, фон телефона и уход ведущего имеют понятное восстановление |
| Защита информации | Игрок/зритель не получает ответы ведущего, закрытые ставки и чужие черновики через HTTP, WebSocket, CDN или MCP |
| Контент | Повреждённый архив, недоступная ссылка и неподдержанный кодек диагностируются до игры |
| Нагрузка | Цели и стенд NFR воспроизводимы; записаны версия приложения, параметры и сырые результаты |
| ИИ | Неверные факты, выдуманные источники, повторы, prompt injection, отмена и превышение бюджета проверены |
| Эксплуатация | Работают жалобы, отзыв доступа, оповещение и восстановление из резервной копии |

## 5. Риски и реакция

| Риск | Сигнал | Действие |
|---|---|---|
| Недооценка SIQ | Много неподдержанных конструкций в корпусе | Уточнить профиль до реализации UI; оценить повторное использование SIPackages |
| Наполнение без прав | Нет разрешения/экспорта, претензия к медиа | Приостановить соответствующий импорт, работать с авторами и разрешёнными материалами |
| Рост трафика | Медиа становится основной статьёй расходов | Производные версии, лимиты, экономный режим, измерение расхода по комнате |
| Споры о кнопке | Жалобы зависят от RTT | Показывать правило, измерять сеть, давать альтернативный режим; не доверять времени клиента |
| Сложность Rust | Прототип задерживается, измеримого выигрыша нет | Выбрать Go/.NET с сохранением контрактов после сравнения |
| Низкое качество ИИ | Много отклонений и неверных источников | Уменьшить генерацию, усилить редакторскую проверку, считать цену принятого вопроса |
| Распыление MVP | Нет полного пользовательского цикла | Закрывать вертикальные сценарии по порядку; новые функции относить в следующую очередь |
| Нехватка модерации | Очередь жалоб растёт | Ограничить новые публикации, привлечь модераторов и авторов; не заменять решение одной моделью |

## 6. Как провести ревью

Начать с таблицы D-01…D-09 в [основном документе](00-PRODUCT-PLAN.md). Достаточно ответить, например: «D-06: встроенный голос обязателен» или «FR-02: нужно 12 игроков». После этого обновляются связанные требования, нагрузка и объём работ.

Для следующей итерации наиболее полезны три вещи: конкретные неудобства текущих решений, допустимые ограничения первой версии и ориентир по бюджету/команде. Их отсутствие не мешает оценить текущий проект документа.
