# Аудит игрового потока SIGame и SI Platform

Аудит от 23 октября 2026. Цель — перенять структуру игрового опыта SIGame, а не копировать оформление, код или звуковые файлы. Основной разрыв: игровая сцена, последовательность представления событий и обнаружимость механик.

> Обновление реализации: UX-01–13 выполнены. Детали и проверки — [журнал выполнения](plans/2026-10-23-sigame-execution.md). Описания «сейчас» и скриншоты ниже фиксируют состояние до изменений. UX-14–15 остаются в плане.

## Среда и границы проверки

localhost:5174 обслуживает checkout «Сохранение-пакетов», а не текущую папку проекта. Для аудита текущая версия запущена на localhost:5175 с отдельными API :8082 и тестовой БД si_audit_20261023. Данные и аккаунты основной БД туда не перенесены. Чужой процесс не изменён.

В SIGame вручную пройдено создание одиночной игры с ботами в роли ведущего, настройки, лобби, старт, выбор вопроса, ответы и счёт. Затем собственная игра закрыта. Особые типы, финал и все варианты анимаций референса не проиграны целиком: ниже для них указаны сведения исходного кода. Исходники SIOnline зафиксированы на ac2e66190056beb141b450b9cb044e0e1e99aa6d; версия живого сайта может отличаться.

## Главный вывод

В нашей текущей версии при viewport 1280×720 высота документа 1494 px, вопрос 870×367 px, пульт 310×688 px. В полноразмерном снимке вопрос начинается примерно на 458 px, счёт уходит ниже основного экрана. У SIGame в проверенном окне 1280×633 центральное табло примерно 754×404 px: проблема не только в ширине, а в занятой навигацией высоте и вертикальном потоке. Ссылку «К содержимому» на нашем тестовом снимке показал фокус клавиатуры; это не постоянный элемент макета.

У нас уже есть короткая CSS-анимация вопроса (0,3 с, fade/translate с учётом reduced motion). Формулировка «анимаций нет» неточна: отсутствует последовательная постановка игровых сцен.

## Типы вопросов: что действительно есть

Встроенный examples/demo.go содержит один раунд, три темы и девять обычных вопросов. Поэтому типы незаметны при первом знакомстве. Редактор позволяет выбрать тип; компилятор internal/playpack/compile.go и тесты internal/game/v2_game_test.go подтверждают перечисленные механики. Произвольные скрипты и все варианты SIGame не поддерживаются.

| Тип | Механика | Доказательство |
|---|---|---|

| Обычный / simple, withButton | Нажатие, устный/письменный ответ, оценка | Браузер: повторный ответ, исключение ошибившегося, переход выбора. |
| Аукцион / stake | Торги и ответ выигравшего | Реализация и unit-тесты; отдельный браузерный прогон нужен. |
| Кот / secret | Передача вопроса и выбор получателя | Реализация и unit-тесты; отдельный браузерный прогон нужен. |
| Всем / forAll | Одновременные ответы нескольких игроков | Реализация и unit-тесты; отдельный браузерный прогон нужен. |
| Без риска / noRisk | Особые правила награды/штрафа | Реализация и unit-тесты; отдельный браузерный прогон нужен. |
| Ставки / stakeAll, финал | Закрытые ставки и ответы; финальное исключение тем | Браузер: приватность, раскрытие, оценка, итоги. |

## Анимации референса и предлагаемый контракт

В исходниках: представление тем примерно по 1900 мс; строки табло появляются с разных сторон за 0,5 с; объект/содержимое имеет fade/scale; постепенный текст обновляется с шагом 100 мс с учётом readingSpeed и паузы. ClientController отдельно объявляет специальные типы и запускает соответствующие звуки. Это наблюдения кода, не измеренные тайминги живого сервера.

Предлагаемая последовательность: пакет → раунд → темы → табло → цена → специальный тип (если нужен) → вопрос → нажатие → ответ → оценка → счёт → табло. Финал имеет собственную последовательность. Обычные переходы 180–350 мс, объявления 1–2 с — стартовая рекомендация для прототипа, не требование копировать референс.

Не скрывать вопрос CSS-задержкой, пока сервер уже отсчитывает ответ. Представление должно иметь серверную фазу и временную отметку; клиент привязывает эффект к идентификатору события/вопроса, не повторяет его при каждом snapshot. При переподключении показывать актуальное состояние. Пауза останавливает зависимые эффекты и медиа; пропуск вступления синхронный для всех. Reduced motion сокращает движение, сохраняя смысл. Второй экран получает только публичную проекцию; приватный ответ не должен мелькать даже на переходе.

## Проверки текущей реализации

Браузерный сценарий rules прошёл: обычный вопрос и повторный ответ, false start, закрытые ставки и ответы, финальное исключение тем, раскрытие/оценка финала, передача ведущего после отключения, результаты; 0 page errors. Отдельный oral-display прошёл: ответ ведущему сразу, немедленная оценка, отсутствие текстового поля у игрока в устном режиме, обновление второго экрана без приватного ответа. Это не приёмка будущих анимаций и не полный браузерный прогон всех специальных типов.

Воспроизводимые сценарии: e2e/rules.mjs и e2e/oral-display.mjs. Локальные логи аудита: .local/audit-current-rules.log и .local/audit-current-oral.log.
