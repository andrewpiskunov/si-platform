# Требования и приёмка

**Статус:** проект требований. `P0` — обязательное для публичного MVP; `P1` — следующая очередь; `P2` — развитие. Числовые значения — предлагаемые критерии, подлежащие проверке прототипом.

## 1. Роли и основной сценарий

Гость играет или наблюдает по приглашению. Зарегистрированный пользователь создаёт комнаты и черновики. Автор управляет своими пакетами. Ведущий управляет конкретной игрой. Модератор рассматривает публикации и жалобы. Администратор управляет инфраструктурой и доступом; действия с чужими данными журналируются.

Сценарий приёмки: автор загружает `.siq` или создаёт пакет с ИИ → исправляет ошибки → проверяет предпросмотр → публикует → ведущий находит пакет → создаёт комнату и выбирает готовую или свою тему оформления → игроки входят с разных устройств → игра доходит до результатов, включая переподключение одного игрока.

| FR-25 / P1 | Конструктор и публичная галерея оформления | Создание без редактирования манифеста, публикация с происхождением ресурсов, модерация и жалобы; отдельное расширение после MVP |

Публикация и скачивание пакета — разные разрешения: автор выбирает, доступен ли полный экспорт посетителям. Игровой клиент не получает архив целиком.

Оформление не связано с темами вопросов `.siq`. Полный сценарий, формат загрузки, область действия между вкладками и поведение при блокировке — в [контракте тем](08-THEMES.md).

## 3. Профиль совместимости P0

Это целевой контракт нашего продукта, а не утверждение о уже работающем конвертере. Основания формата — [документация SIPackages](https://raw.githubusercontent.com/VladimirKhil/SI/master/src/Common/SIPackages/README.md) и [типы вопросов в исходном коде](https://github.com/VladimirKhil/SI/blob/7f8cda975fdd71aef69fa4eef0572d41417d8900/src/Common/SIPackages/Core/QuestionTypes.cs).

| Конструкция | Импорт / редактирование / игра / экспорт |
|---|---|
| SIQ v4 и v5 | Поддержка перечисленного профиля; v4 преобразуется во внутреннюю модель, экспортируется в v5 |
| Раунды, темы, цена, авторы, источники, комментарии ведущему | Сохранение; приватные комментарии не попадают к игрокам |
| Обычный вопрос: default/simple/withButton | P0; точное соответствие поведения проверяется эталонными сценариями |
| Ставка: auction/stake; общая скрытая ставка: stakeAll | P0; пределы ставки и раскрытие — серверные правила |
| Секретный вопрос: cat/bagcat/secret | P0 для стандартных вариантов; неизвестные параметры отмечаются как несовместимость |
| Вопрос всем; без риска: forAll, sponsored/noRisk | P0; очки и штрафы учитывают параметры |
| Стандартный финал | P0: выбор темы, закрытые ставки и ответы, раскрытие, начисление очков |
| Текст, картинки, аудио, видео; несколько шагов вопроса/ответа | P0; соблюдаются порядок, длительности и граница раскрытия ответа |
| Кириллица и кодированные имена, относительные ссылки, метаданные | P0; отсутствующие файлы и неоднозначные имена выдаются в отчёт |
| Внешние медиа | Импорт ссылки и диагностика P0; игра только после разрешённой загрузки и проверки копии либо замены |
| Специальные варианты secretPublicPrice/secretNoQuestion, forYourself | P1; в MVP распознаются, но не обещаются к проигрыванию |
| Выбор вариантов, числовой ответ, точка на изображении | P1; ручной текстовый ответ P0 не считается полной поддержкой этих форматов |
| HTML, произвольный script, неизвестные типы/версии | Заблокированное исполнение; оригинал доступен владельцу, проблемные элементы перечислены |

Корпус: минимум 100 законно полученных пакетов, включая 30 специально подготовленных крайних случаев. Все фикстуры P0 должны проходить; вне профиля каждый случай обязан явно диагностироваться. Отдельно измеряется доля полностью играбельных пакетов в репрезентативной выборке — целевая ≥95%; если она ниже, расширяем профиль или пересматриваем объём MVP до публичного обещания совместимости.

Экспорт проверяется открытием в SIQuester 6.9.1 и прохождением сценариев в SIGame 7.13.12; версия веб-клиента фиксируется во время испытаний. Это тестовая база, которую обновляют при изменении формата.

## 5. Нефункциональные требования

`p95` означает, что 95% измерений укладываются в значение. Все цели относятся к определённому профилю нагрузки, а не к произвольному интернет-соединению.

| ID | Цель | Как принимаем |
|---|---|---|
| NFR-01 | 10 000 WebSocket-подключений, 1 000 активных комнат | Профиль и оборудование из архитектуры; час плато и 8 часов проверки роста памяти |
| NFR-02 | Серверная обработка обычной команды p95 ≤30 мс, p99 ≤75 мс | От входа в обработчик владельца комнаты до сохранения и постановки события в исходящую очередь; без сети пользователя; окно случайного выбора измеряется отдельно |
| NFR-03 | Нажатие → подтверждённый результат p95 ≤200 мс | Режим первого поступления, RTT ≤100 мс, jitter ≤20 мс, потери ≤1%; сценарии RTT 200/400 мс отчётны, без обещания тех же 200 мс |
| NFR-04 | Возврат после восстановления сети p95 ≤3 с; после потери узла ≤15 с | Сохраняются подтверждённые решения; тесты разрыва, повторов и смены владельца комнаты |
| NFR-05 | Стартовая загрузка игровой страницы ≤250 KiB JS после Brotli; LCP ≤2,5 с, INP ≤200 мс на p75 | Без медиа и редактора; отдельный бюджет маршрута; лабораторные тесты на среднем Android/iPhone при 10 Мбит/с и RTT 100 мс, затем полевые метрики |
| NFR-06 | API каталога p95 ≤300 мс | 100 000 синтетических карточек, 100 запросов/с, отдельный замер холодного/тёплого кеша |
| NFR-07 | RSS каждого игрового узла ≤4 GiB на стенде NFR-01 | Включая состояние комнат и очереди, без БД/CDN; отдельно учитываются память ядра, TLS-прокси и фоновые задачи |
| NFR-08 | Доступность критического пути 99,9% за месяц после публичного запуска | Вход в комнату, управление игрой и восстановление; плановые работы включены; месячная история мониторинга |
| NFR-09 | Нет потери подтверждённых игровых решений при сбое процесса | Подтверждение после записи; для потери всей площадки: RPO ≤5 минут, RTO ≤60 минут с проверкой восстановления резервной копии |
| NFR-10 | Безопасные загрузки и разграничение доступа | Отрицательные тесты ZIP/XML, XSS/SSRF, приватных ответов, ролей и MCP; лимиты ниже |
| NFR-11 | Современные браузеры и доступность | На выпуске последние 2 стабильные версии Chrome, Edge, Firefox, Safari; Android Chrome и iOS Safari; клавиатура, фокус, контраст, reduced motion; целевой WCAG 2.2 AA |
| NFR-12 | Измеримые расходы и наблюдаемость | Метрики комнат, соединений, задержек, очередей, памяти, ГБ, ИИ; алерты и ответственный за инцидент |
| NFR-13 | Оформление сохраняет скорость и доступность игры | Первый показ темы: ≤1 MiB файлов на мобильном, ≤2 MiB на компьютере; NFR-03/05/11 проверяются с темами; недоступный декор не блокирует кнопку и не меняет состояние |

Ограничения браузерного autoplay учитываются в проверке звука; фоновая вкладка и заблокированный телефон не должны выглядеть как активный готовый игрок. [MDN](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Autoplay). Ориентир доступности: [WCAG 2.2](https://www.w3.org/TR/WCAG22/).

## 6. Предлагаемые лимиты MVP

| Объект | Лимит |
|---|---|
| Оригинал `.siq` | 250 MiB; возобновляемая загрузка |
| Распакованный пакет | 1 GiB, до 5 000 файлов, XML до 10 MiB, до 2 000 вопросов; вложенные архивы не раскрываются |
| Отдельный медиафайл | 100 MiB и до 10 минут аудио/видео |
| WebSocket | Входящее сообщение ≤16 KiB; 10 команд/с на участника, всплеск до 20; лимиты на IP не заменяют лимиты аккаунта |
| Исходящая очередь клиента | До 64 KiB; объединять некритичные обновления, затем переподключать медленного клиента со снимком состояния |
| ИИ-задание | До 100 вопросов; явный предел стоимости задания и месячная квота; повтор после сбоя не списывает расход повторно без учёта статуса провайдера |
| Тема оформления | ZIP ≤5 MiB, распаковка ≤20 MiB / 50 файлов, JSON ≤64 KiB; изображение ≤4 Мп / 2 MiB; только разрешённые параметры и статические PNG/JPEG/WebP |

Превышение показывает понятную причину и путь исправления. Лимиты пересматриваются по корпусу файлов; увеличение не отменяет потоковую обработку и изоляцию.

Связь с бизнес-целями: `BR-01/03 → FR-01…15`; `BR-02 → FR-03 + профиль`; `BR-04/08 → FR-06/07/16/20`; `BR-05 → FR-17 + продуктовые метрики`; `BR-06 → FR-18 + NFR-07/12`; `BR-07 → FR-08…13 + NFR-01…04/09`; `BR-09 → FR-23/24 + NFR-13`.

## 7. Технологические ограничения

Серверная бизнес-логика, игровой движок и фоновые задания реализуются на **Go** — решение пользователя. Выбранные HTTP/WebSocket/SQL-компоненты и условия выбора S3-провайдера описаны в [стеке](06-TECH-STACK.md). Фронтенд пока на ревью: [сравнение вариантов](07-FRONTEND-CHOICE.md).

Перед основной разработкой подтверждаем совместную работу компонентов: авторизованный WebSocket, запись решения в PostgreSQL до подтверждения, восстановление, загрузка файла частями в выбранное хранилище и приватная выдача медиа. Прототип обязан сохранять P0-лимит 12 игроков; смена библиотеки не меняет продуктовые требования.

## 8. Уточнение игрового UX от 21.10.2026

Обязательные новые пользовательские требования к дальнейшей разработке: QR-приглашение перед стартом; отдельный публичный экран и приватная панель ведущего; центральное табло; устная игра с ручной оценкой и режим автоматической проверки ответов игроков; явные состояния кнопки и фальстарта. Спецификация, ограничения и критерии приёмки — [Игровой интерфейс](32-GAME-EXPERIENCE.md). Эти пункты записаны в требования, но пока не помечены реализованными; порядок и границы выпуска уточняются после прототипа.
