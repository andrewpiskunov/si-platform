# Импорт SIBrowser в публичный каталог

Статус: согласован пользователем; реализация описана в `Docs/35-SIBROWSER-SYNC.md`.

## Задача и согласованные решения

Пользователь хочет первоначально импортировать все доступные пакеты с https://www.sibrowser.ru/, затем ежедневно добавлять новые. Успешно обработанные пакеты должны автоматически появляться в публичном каталоге, без ручной модерации. Выбран отдельный Go CLI `sibrowser-sync`, запускаемый cron.

## Рассмотренные подходы

1. **Отдельная команда + cron (выбран).** Независимый жизненный цикл, ручной запуск полного обхода, удобный контроль повторов и отчётов. Нужны настройка расписания и постоянное хранилище состояния.
2. Планировщик внутри HTTP-сервера. Меньше внешней конфигурации, но расписание зависит от перезапусков сервера и требует координации реплик. Не выбран.

## Что есть сейчас

`internal/catalogueimport` передаёт локальные SIQ через API загрузок; `internal/ingest` разбирает SIQ, сохраняет оригиналы и обрабатывает медиа. `catalogue_imports` обеспечивает повторяемость по владельцу, namespace и external_id. Результат — приватный черновик. Обычная публикация требует подтверждения прав и пользовательской сессии; PAT не даёт права модерации.

На владельца сейчас действуют лимиты 200 пакетов и 10 GiB, на архив — 250 MiB. Простой цикл над существующим CLI не обеспечит полный импорт и публикацию.

На 2026-10-23 HTML главной страницы SIBrowser содержит карточки `/packages/<id>`, ссылки `/packages/<id>/direct_download` и пагинацию `?page=...` (последняя ссылка — 2288). Эти значения — наблюдение, не константы реализации. `robots.txt` содержит `Disallow: */direct_download`; это ограничение источника должно быть явно отражено в инструкции эксплуатации. Доступность скачивания, редиректы и размер полного архива пока не проверены. Разработка и тестирование не запускают массовое скачивание или публикацию в рабочем окружении.

## Предлагаемое устройство

Команда использует `DATABASE_URL`, настроенный origin API и токен отдельного служебного администратора; секреты только в окружении. PostgreSQL хранит состояние обхода и записей. SIQ передаются в работающий сервер через существующий ingest, который остаётся единственным обработчиком архивов и медиа. CLI не поднимает второй ingest worker и не пишет напрямую в blob-хранилище.

Добавляется узкая операция автоматической публикации импортированной записи. Она доступна только настроенному владельцу SIBrowser с действующим токеном и ролью admin, проверяет принадлежность записи этому источнику, текущую ревизию, готовность медиа, играбельность и отсутствие блокировки/удаления. Она не даёт токену общие возможности модерации. Обновление статуса публикации и аудит выполняются транзакционно. Повтор после неопределённого HTTP-ответа возвращает уже опубликованный результат.

Автоматическая публикация — отдельный тип происхождения `external_import`, а не подстановка `rights.confirmed=true`. Сохраняются автор, URL карточки, внешний ID, SHA256, время обнаружения и импорта. Неизвестная лицензия отмечается как неизвестная, не как CC0/CC-BY. Существующий ручной импорт с обязательными полями разрешения остаётся отдельным контрактом. Для SIBrowser добавляется типизированный контракт происхождения, а не фиктивные значения `permission_basis`. Отображение источника использует имеющиеся поля карточки; при необходимости добавляется краткая отметка импорта. Предлагаемый default: пакет доступен для игры, скачивание оригинала с нашего сайта выключено до отдельной настройки оператора.

## Состояние и отсутствие дубликатов

- Уникальный ключ источника `(source, external_id)` глобален для источника, а не зависит от запуска. Владелец закрепляется при настройке; смена владельца не создаёт вторую копию.
- Запись содержит метаданные, этап, число попыток, следующую попытку, безопасный код ошибки, upload_id, pack_id и revision. Этапы: discovered → downloaded → importing → imported → published; отдельно retryable, rejected и suppressed.
- Скачанный файл и SHA фиксируются до запроса на импорт. Метаданные для повторной отправки неизменны. Потеря локального файла требует повторной загрузки с проверкой SHA; изменившееся содержимое не отправляется под прежним ключом.
- Локальные файлы временные и ограниченные по размеру; после подтверждённого импорта удаляются. Статус PostgreSQL и серверные receipts обеспечивают восстановление после потери каталога временных файлов.
- Удалённый, снятый с публикации или заблокированный оператором пакет не публикуется заново. Автоматическое снятие статуса suppressed запрещено. Отличать начальный приватный импорт от последующего ручного снятия публикации нужно по аудиту/состоянию публикации, а не только `published_revision`.
- Сетевые ошибки, 429 и 5xx повторяются с ограниченным backoff и Retry-After. Битый/неподдерживаемый архив — rejected, автоматического бесконечного повтора нет. Повтор обработки после исправления инфраструктуры — явный retry с сохранением того же пакета/receipt, без генерации нового external_id ради обхода ошибки.

## Полный и ежедневный обход

`--mode=full` проходит реальные ссылки next до конца. Список ID страницы записывается атомарно с checkpoint до перехода дальше. Прерывание возобновляется с сохранённой страницы с перекрытием; по окончании выполняется проверка начала выдачи для новых публикаций, появившихся во время обхода. Успешный full повторно запускает обход с начала, но не скачивает уже импортированное. Пустая неожиданная выдача/изменение разметки — ошибка, а не успешное завершение.

`--mode=incremental` сначала возобновляет отложенные записи, затем начинает с первой страницы. После успешного полного импорта проверяет новые страницы до границы прошлого успешного обхода с перекрытием в несколько полностью известных страниц. Не останавливается на первом знакомом ID и не полагается только на дату публикации или максимальный ID. Незавершённые записи в перекрытии остаются в очереди. До завершения первого полного обхода incremental обходит выдачу целиком либо использует checkpoint bootstrap.

Ограничение: быстрый режим предполагает, что новые публикации появляются в начале выдачи по дате. Позднюю вставку в старую часть списка выявляет повторный full; документация рекомендует периодическую полную сверку. Обновление содержимого уже опубликованных пакетов и удаление вслед за удалением на источнике в первую версию не входят.

Один активный процесс на источник, защищённый PostgreSQL advisory lock на выделенном соединении. Потеря соединения блокировки отменяет работу. Full и incremental используют один lock. Второй запуск завершает работу с диагностикой без выполнения импорта. Параметры `--max-pages`, `--max-items`, `--timeout` позволяют ограничить объём; достижение лимита сохраняет checkpoint, но не отмечает полный обход завершённым.

## HTTP и ресурсы

HTML разбирается структурным парсером, без запуска JS. Карточки извлекаются только из основного списка, не из блока похожих пакетов. Пагинация ограничена origin и ожидаемым маршрутом, защита от циклов. HTML и архивы имеют лимиты размера, таймауты и отмену через context. HTML вместо SIQ не принимается.

Предлагаемые defaults: последовательные загрузки, интервал минимум 1 секунда между запросами к источнику, идентифицирующий User-Agent, до 3 непосредственных попыток; дальнейшие повторы сохраняются до следующего запуска. Политика допустимых download-hosts и редиректов фиксируется после проверки реальной цепочки скачивания. Нельзя обращаться к loopback/private/link-local адресам, в том числе после DNS/редиректа, или передавать токен платформы внешнему серверу. Тестовый транспорт внедряется отдельно от production-политики.

Для настроенного служебного владельца добавляются отдельные положительные квоты пакетов и общего логического объёма; их явно задаёт оператор согласно доступному диску. Общие пользовательские defaults остаются 200/10 GiB. Проверки ingest, создания/обновления пакета, медиа и Usage должны использовать единый resolver квот. Лимит архива 250 MiB и правила проверки SIQ остаются. Превышающие лимит пакеты отражаются в отчёте; «полный обход» не означает успешную обработку заведомо неподдерживаемых файлов. Исчерпание общей квоты останавливает импорт как инфраструктурная ошибка, не отбрасывает остальные записи.

## Эксплуатация

CLI включается в Docker image. Добавляется opt-in compose service/profile с доступом к БД, API и отдельному scratch-volume. Внутренний HTTP между контейнерами допускается только явно настроенным режимом; default HTTPS сохраняется, токены не следуют редиректам. Миграции выполняются штатной командой перед запуском; cron вызывает `docker compose run --rm ... --mode=incremental`. Время запуска указывается в примере как настройка оператора, расписание на машине пользователя автоматически не устанавливается.

Отчёт JSON/JSONL: run_id, режим, количество просмотренных/новых/опубликованных/пропущенных/ошибочных записей, checkpoint, признак завершения обхода, ID и этап каждой ошибки. Секреты и подписанные download URL не логируются. Код 0 — текущая работа завершена без неразрешённых ошибок; отдельные ненулевые коды — неполный запуск/ошибки, занятый lock, ошибка конфигурации. Исторические rejected считаются отдельно и не делают все будущие запуски неуспешными.

## Проверка реализации

1. HTML fixtures: карточки, пагинация, конец, изменение разметки, дубликаты, похожие пакеты, новые записи в перекрытии.
2. HTTP fixture server: редиректы, неверный origin/IP, Retry-After, timeout, отмена, превышение размера, HTML вместо архива.
3. Реальный PostgreSQL: уникальность, lock двух процессов, потеря lease/соединения, checkpoint, восстановление на каждом этапе, смена владельца, удаление/блокировка/withdraw, новые квоты.
4. Синтетический SIQ через настоящий HTTP API и ingest → публичный каталог → доступность игры. Повтор full/incremental не создаёт пакеты или повторные публикации. Неподдерживаемые медиа остаются диагностируемой ошибкой и не публикуются.
5. Проверка отзыва токена/роли, доступа другого владельца и невозможности публикации произвольного черновика новым endpoint.
6. Сборка CLI/container, пример cron, документация настройки, ограничений и восстановления. Реальная массовая загрузка не является тестом реализации.

## Делегировано реализации

Точные названия таблиц/endpoint/флагов и коды ошибок; размер перекрытия; параметры backoff; выбор HTML-библиотеки из имеющихся зависимостей; минимальные изменения UI для честного отображения происхождения. Все перечисленные defaults — предложение разработчика, а не отдельно высказанные требования пользователя.
