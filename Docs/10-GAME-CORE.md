# Первый работающий этап: игровое ядро

Реализован Go-сервер для технического прототипа: ведущий, до 12 игроков и 20 зрителей, текстовый вопрос, нажатие, решение ведущего, счёт и переподключение. Решения хранятся в PostgreSQL. Графический интерфейс, импорт SIQ, каталог, редактор, темы и ИИ относятся к следующим этапам.

## Запуск

Вариант с Docker Compose:

```sh
cp .env.example .env
docker compose up --build -d
docker compose run --rm --no-deps --entrypoint /app/demo api -url http://api:8080
```

API доступен на `http://127.0.0.1:8080`, проверка готовности — `/readyz`. Корневой URL пока не содержит игровой страницы. Compose сначала запускает PostgreSQL, затем миграции, затем сервер. Остановка — `docker compose down`; данные сохраняются в именованном томе.

Вариант с установленными Go 1.27.3 и PostgreSQL 18:

```sh
export DATABASE_URL='postgres://USER:PASSWORD@127.0.0.1:5432/si?sslmode=disable'
go run ./cmd/migrate
go run ./cmd/server
```

В другом терминале: `go run ./cmd/demo`. База `si` должна уже существовать. `.env` автоматически читается Compose и Makefile; при прямом `go run` переменные нужно экспортировать. Команды `make migrate`, `make run`, `make demo` — сокращения при наличии Make.

`LISTEN_ADDR` по умолчанию `127.0.0.1:8080`. `ALLOWED_ORIGIN` задаёт точный допустимый браузерный Origin; без него разрешается Origin того же адреса и схемы, что у запроса. CLI может подключаться без Origin. Для выхода за локальную машину понадобится TLS-прокси и следующая итерация управления аккаунтами/сессиями.

Демо создаёт комнату, подключает 12 игроков, отправляет конкурентные нажатия, начисляет победителю 100 очков, повторяет решение и переподключает победителя. Итоговый JSON содержит `winners:1`, `score:100`, `duplicate_safe:true`, `reconnect_restored:true`; токены в вывод не попадают.

## HTTP

| Маршрут | Тело / результат |
|---|---|
| `POST /api/rooms` | `{ "host_name": "Ведущий" }` → `room_id`, `participant_id`, `token`, `invite_token` |
| `POST /api/rooms/{room_id}/participants` | `{ "name": "Игрок", "role": "player", "invite_token": "..." }` → `room_id`, `participant_id`, `token`; роль также может быть `spectator` |
| `GET /healthz` | Живость процесса |
| `GET /readyz` | Доступность БД и приём запросов процессом |

POST требует `Content-Type: application/json`. Успех создания/входа — 201; ошибки содержат `{ "error": "код" }`. Новые игроки входят в лобби или между вопросами; уже занятое место восстанавливается токеном через WS. Зритель может присоединиться во время вопроса.

Токен участника — секрет доступа к его роли, приглашение — отдельный секрет входа. Сервер хранит только SHA-256 токенов; клиент сохраняет полученный токен для восстановления. В этой итерации нет ротации, срока действия и восстановления потерянного токена. Создание комнаты/нового места пока не идемпотентно: после потери HTTP-ответа повтор может создать ещё одну сущность. Идемпотентны именно игровые команды.

## WebSocket

Адрес: `ws://127.0.0.1:8080/api/rooms/{room_id}/ws` (через TLS-прокси — `wss://…`). Первый текстовый кадр в течение пяти секунд:

```json
{"v":1,"type":"authenticate","token":"ТОКЕН_УЧАСТНИКА"}
```

После проверки сервер отправляет `snapshot`: `v`, `server_time` в Unix milliseconds, `state`. Состояние содержит `room_id`, `seq`, `phase`, `participants`, `question`, `winner`, `you`. Поле `question.answer` до решения есть только у ведущего.

| Команда | Поля помимо `v:1`, `id`, `type` | Роль |
|---|---|---|
| `open_question` | `question_id`, `text`, `answer`, `value` | Ведущий |
| `buzz` | `question_id` | Игрок |
| `judge` | `question_id`, `correct: true/false` | Ведущий |
| `pause`, `resume`, `finish` | Нет | Ведущий |

Пример:

```json
{"v":1,"id":"open-001","type":"open_question","question_id":"q-001","text":"Сколько будет 2 + 2?","answer":"4","value":100}
```

Фазы: `lobby → open → answering → resolved`; `paused` сохраняет предыдущее состояние, `finished` завершает комнату. Для первого открытия нужны минимум два игрока. В простом режиме на вопрос приходится одна попытка: +цена за правильный ответ, −цена за неправильный; последующее открытие использует новый `question_id`.

Ответ на команду — `result` с `command_id`, `code`, `result_seq`, `duplicate` и актуальным `state`. При успехе `code=ok`; ошибка правил возвращает свой код без изменения состояния. Ошибка формата, лимита или инфраструктуры приходит как `error`. События другим участникам передаются актуальными снимками.

ID команды уникален внутри комнаты и участника. Повтор с теми же полями возвращает прежний результат, с изменёнными — `command_conflict`. `result_seq` при повторе относится к первоначальному решению, `state.seq` может быть новее. Клиент применяет снимки монотонно по `state.seq` и отдельно учитывает подтверждения команд.

## Долговечность и восстановление

Один обработчик комнаты последовательно выполняет команды. Транзакция PostgreSQL блокирует строку комнаты, проверяет повтор, сохраняет снимок, событие и результат команды. Положительный ответ отправляется после commit. При неопределённом исходе соединения клиент повторяет **тот же ID**, а не создаёт новый.

При переподключении достаточно прежнего токена: сервер отправляет полный актуальный снимок. Места, роль, счёт и ID обработанных команд сохраняются после перезапуска процесса. Если ведущий отключил последнее соединение, активный вопрос ставится на паузу. При старте сервера активные вопросы также приостанавливаются; продолжение требует команды ведущего.

Прототип допускает один серверный процесс на БД/схему. Advisory lock не пускает вторую копию; возрастающая эпоха дополнительно блокирует записи прежнего владельца после смены. Heartbeat владельца прекращает обслуживание при потере соединения. Это не готовая кластерная маршрутизация комнат.

## Ограничения прототипа

- WS: 16 KiB на вход, 64 KiB очереди на соединение, 10 команд/с с burst 20. Некорректные кадры тоже ограничиваются. Медленное соединение закрывается.
- До двух соединений одной роли/участника; до 10 000 сокетов процесса как предохранительный лимит, **не измеренная вместимость**.
- До 1 000 сохранённых комнат в БД прототипа, до 2 000 вопросов в комнате. Автоматической очистки и удаления комнат пока нет.
- Имя — 1–32 символа, цена — 1–100 000, текст/ответ — до 4 096 байт. Во входных JSON запрещены неизвестные поля.
- Счёт, правила полного SIGame, голос, UI и доставка медиа не считаются завершёнными сверх описанного простого сценария. Публичный запуск требует следующих этапов дорожной карты.

## Проверки и сопровождение

```sh
go test ./...
export TEST_DATABASE_URL='postgres://USER:PASSWORD@127.0.0.1:5432/si_test?sslmode=disable'
go test -race ./...
go vet ./...
go build ./cmd/...
```

Без `TEST_DATABASE_URL` PostgreSQL/WS-тесты явно пропускаются. Использовать отдельную тестовую БД: каждый тест создаёт случайную схему и удаляет её после выполнения. Покрыты гонка 12 нажатий, одновременное заполнение комнаты, роли, скрытый ответ, повторы, ошибка транзакции, переподключение, новый экземпляр сервера, уход ведущего, Origin, лимиты и устаревший владелец.

SQL описан в `sql/queries.sql`; сгенерированные файлы находятся в `internal/storage/db`. Генерация: `go run github.com/sqlc-dev/sqlc/cmd/sqlc@v1.31.1 generate`. Миграции goose лежат в `migrations` и запускаются отдельной командой. Версии runtime-зависимостей закреплены в `go.mod`/`go.sum`.
