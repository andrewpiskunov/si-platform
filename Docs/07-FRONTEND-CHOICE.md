# Почему предложен SvelteKit и какие есть альтернативы

**Статус:** рекомендация для обсуждения, фронтенд пользователем ещё не утверждён. Go на сервере уже выбран и не ограничивает нас конкретным UI-фреймворком.

## 1. Основание рекомендации

Для проекта предлагается **SvelteKit + TypeScript**: много собственного игрового интерфейса, интерактивное табло, мобильная кнопка и темы оформления. Нужны понятная модель состояния, контролируемый размер игрового маршрута и возможность отдельно загружать тяжёлый редактор.

Svelte — компонентный фреймворк с компилятором; SvelteKit добавляет маршруты и режимы рендеринга приложения. Компиляция позволяет готовить код обновления интерфейса заранее, однако сама по себе не гарантирует меньшую сборку или лучший INP в нашем продукте. Библиотеки, медиа и организация обновлений могут перевесить разницу фреймворков. [Svelte](https://svelte.dev/docs/svelte/overview), [SvelteKit](https://svelte.dev/docs/kit/introduction).

Моя оценка: Svelte удобен для небольшой команды, которая создаёт собственные компоненты и не связана существующим React/Vue-кодом. Это рабочее допущение — состав и опыт команды пока неизвестны.

## 2. Сравнение для нашей задачи

| Вариант | Чем привлекателен | Чем платим / что проверить |
|---|---|---|
| **Svelte + SvelteKit** | Компактная запись интерактивных компонентов, стили рядом с компонентом, единая маршрутизация каталога и игры | Проверить наличие подходящих редактора текста, drag-and-drop, виртуализации и доступных компонентов; React-компонент нельзя просто подключить как Svelte-компонент |
| **React + React Router, сборка Vite** | Прямой доступ к React-компонентам; удобно при опыте команды и зависимости от сложного готового редактора | Нужно дисциплинированно организовать состояние и обновления; Vite сам по себе не задаёт архитектуру приложения |
| **React + Next.js** | Интегрированные серверные страницы, маршрутизация и Server Components для каталога | Добавляются границы server/client и правила кеширования; важно не дублировать бизнес-логику Go в Next |
| **Vue + Nuxt** | Шаблоны и реактивная модель, компонентные файлы, серверный и гибридный рендеринг | Как и для Svelte, проверяем нужные интеграции и опыт команды; преимущества Vue не устраняют работу над состоянием и загрузками |

React Router поддерживает клиентский, серверный и предварительный рендеринг: **React не требует Next.js**, а React Router не ограничен SPA. [React Router](https://reactrouter.com/start/framework/rendering).

Next.js позволяет оставлять часть интерфейса на сервере и уменьшать клиентский JavaScript, но интерактивные элементы требуют клиентских компонентов. Поэтому неверно заранее объявлять любую React-сборку тяжелее Svelte. [Next.js](https://nextjs.org/docs/app/getting-started/server-and-client-components).

Vue/Nuxt — полноценная альтернатива с универсальным и гибридным рендерингом. Если команда лучше знает Vue и необходимые компоненты подходят, выбирать Svelte ради самого названия нет причины. [Vue](https://vuejs.org/guide/introduction.html), [Nuxt](https://learn.nuxt.com/en/concepts/rendering-modes).

## 3. Где Svelte может оказаться хуже

Главный риск — цена сборки авторского редактора. Проверяем конкретные возможности: дерево пакета, перестановку вопросов с клавиатуры, редактирование текста, вставку медиа, отмену и большие списки. Если в React уже есть подходящая библиотека, а в Svelte приходится писать и сопровождать адаптер, первоначальная экономия кода исчезнет.

Для обычных диалогов, меню и полей кандидаты — [Bits UI](https://www.bits-ui.com/docs/introduction) и [shadcn-svelte](https://www.shadcn-svelte.com/docs). Их наличие не доказывает готовность всего редактора. Копируемые компоненты также требуют собственного сопровождения и проверки доступности.

Второй риск — опыт команды. Скорость разработки и исправления ошибок важнее небольшого преимущества в искусственном тесте. Третий — ошибки реактивности и SSR: состояние комнаты нельзя хранить в серверном singleton, общем для разных посетителей. Это требование к архитектуре при любом выбранном фреймворке.

## 4. Как фронтенд сосуществует с Go

Предлагаемая схема для SvelteKit: каталог и публичные карточки рендерятся отдельным Node.js-процессом; игровое состояние живёт в Go, а браузер соединяется с ним напрямую по WSS. Node не пересылает каждое игровое событие. Go отвечает за права, правила, запись и восстановление. [SvelteKit adapter-node](https://svelte.dev/docs/kit/adapter-node).

SSR полезен для первого показа и индексирования каталога. Он не ускоряет сетевой путь нажатия после загрузки страницы. На задержку влияют RTT, очередь комнаты, запись в БД и работа браузера; на вместимость сервера — организация соединений и состояние Go.

При переходе на React Router, Next или Nuxt эти границы можно сохранить. Части приложения не обязаны использовать один режим рендеринга.

## 5. Пользовательские темы

Требование готовых и загружаемых тем **не привязывает нас к Svelte**. Палитра задаётся проверенными дизайн-токенами, изображения — разрешёнными ресурсами; компоненты используют общие CSS-переменные и семантические стили. Это реализуемо во всех сравниваемых вариантах. [CSS custom properties](https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Cascading_variables/Using_custom_properties).

Тема меняет всю оболочку игровой сессии: лобби, навигацию, табло, карточки игроков, вопрос, меню и результаты. Положение кнопки, доступность и правила игры остаются контролируемыми продуктом. Детали загрузки, ограничения и приёмка — в [требованиях к темам](08-THEMES.md).

## 6. Как принять окончательное решение

Сначала проверяем нужные компоненты и опыт команды. Затем делаем один небольшой вертикальный прототип на SvelteKit:

1. Табло с 12 игроками, таймером, WebSocket-событиями и переподключением; отдельно короткий всплеск 20 событий/с.
2. Редактор с 500 вопросами: открыть, переставить, изменить, отменить и сохранить; это тест, не новый лимит пакета.
3. Карточку каталога с SSR и ленивой загрузкой редактора.
4. Классическую, пиратскую и загруженную тему; мобильный экран, диалоги, reduced motion и возврат к базовой теме.

Фиксируем production-сборку, устройство и сеть. Проверяем бюджет игрового JS ≤250 KiB после Brotli, LCP/INP по NFR-05, память, доступность и трудоёмкость интеграций. Тема имеет отдельный бюджет файлов; скрывать её влияние на LCP нельзя.

Если есть конкретный провал или сильная зависимость от React/Vue, повторяем проблемный сценарий на соответствующей альтернативе с теми же данными и условиями. Строить четыре полных приложения ради выбора не требуется.

**Текущая рекомендация:** оставить SvelteKit первым кандидатом. **Причина выбрать React Router вместо него:** существенная экономия на нужных компонентах или опыте команды. **Причина выбрать Next:** заметная потребность в его серверных возможностях. **Причина выбрать Nuxt:** подходящий Vue-стек и команда. Ни один из вариантов заранее не объявлен победителем измерений.
