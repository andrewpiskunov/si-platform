# Наблюдаемость сервиса

Этап закрывает техническую основу NFR-12 и измерения для NFR-01…09. Метрики не доказывают достижение нагрузочных целей: результаты стенда фиксируются отдельно. Сегодня игровой движок имеет одного активного владельца БД с fencing epoch; запуск трёх активных игровых процессов не поддерживается. Предложение трёх узлов в архитектуре остаётся целевой конфигурацией, требующей отдельного распределения комнат.

## Что измеряем

- HTTP: число запросов по ограниченной категории/status class, задержка, принятые/выданные байты приложения. WebSocket upgrade отделён от длительности HTTP-запроса. Трафик TLS/CDN и ядра ОС сюда не входит.
- Игра: текущие подключения и загруженные комнаты, длины очередей, задержка ожидания и выполнения задания комнаты, отдельная категория обычных WS-команд. Выполнение измеряется от приёма задания владельцем комнаты до сохранения/постановки результата; выбранное окно случайного победителя и сеть пользователя требуют отдельных испытаний.
- Go/процесс: RSS, CPU, goroutines, heap/GC, файловые дескрипторы через стандартные коллекторы.
- PostgreSQL: занятость/ожидание пула; агрегированные очереди загрузок и ИИ, известные расходы и удержанные резервы ИИ, логические байты версий пакетов/тем. Физическое S3-хранилище/версии/egress измеряются средствами провайдера.
- Обновление агрегатов: успех, длительность и время последнего успеха. При недоступной БД старое значение не превращается в ложный ноль.

Никаких user/room/pack IDs, IP, токенов, текстов вопросов, SQL или произвольных URL в метках. Категории и наборы меток фиксированы. Инструментирование не выполняет запросы БД внутри игрового обработчика; фоновые агрегаты ограничены временем, scrape не обращается к БД.

## Доступ и эксплуатация

Отдельный HTTP listener `METRICS_ADDR`, выключенный при пустом значении; не включается в публичные маршруты или Caddy. `METRICS_TOKEN` — отдельный секрет не короче 32 символов, обязателен при включении даже на loopback. Только GET `/metrics`, Bearer header, no-store; без cookies, query token, CORS и pprof. На scrape — до двух одновременных запросов и 5 секунд. Доступ через локальную/защищённую операторскую сеть; HTTP не заменяет TLS/VPN для удалённого сборщика.

Официальный `prometheus/client_golang v1.25.0`, отдельный registry на сервер вместо глобального реестра. Фиксированные histogram buckets в секундах включают 0.03/0.075/0.2/0.3/3/15 для наших целей. Агрегаты БД обновляются одним фоновым проходом не чаще раза в 15 секунд, с общим лимитом 2 секунды и остановкой при shutdown. Ошибки наблюдения не останавливают игру; невозможность открыть явно настроенный listener считается ошибкой запуска.

Поставляем пример scrape config, alert rules и краткий runbook: недоступность, p95/ошибки, RSS, очереди, устаревшие агрегаты, незавершённые ИИ-резервы. Правила показывают предполагаемые пороги, а не уже достигнутый SLO. Получатель алертов и on-call назначаются владельцем перед публикацией; автоматическая отправка людям здесь не включается.

## Приёмка

Проверяем реальные HTTP/WS/PG переходы, bounded cardinality при произвольных путях, отсутствие секретов в exposition, недоступность endpoint без отдельного токена, работу с отменой/недоступной БД и корректное завершение. Обычные API/игровые регрессии сохраняются. Реальный Prometheus/cloud dashboard/месячная доступность подтверждаются отдельно.
